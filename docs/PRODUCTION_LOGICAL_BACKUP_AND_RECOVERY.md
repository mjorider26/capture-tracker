# Production logical backup and recovery

Capture Tracker production remains on Neon Free. The available provider history is the current Free-plan window; it is not a seven-day PITR policy and no paid Neon snapshot schedule is used.

## Backup procedure

Run the backup only from native Linux/WSL. Provide the direct, unpooled TLS production connection only to that process through `CAPTURE_TRACKER_PRODUCTION_DIRECT_DATABASE_URL`; never put it in a Windows environment file, repository file, command argument, archive name, or log.

The approved private WSL configuration must export every required variable to the backup process; a shell-local assignment is not sufficient for the Node process. Load the protected `0600` configuration in the same shell session, verify required names by presence only, and never print their values. The backup preflight fails explicitly at `BACKUP_PREFLIGHT` when a required process variable is absent.

`tsx scripts/backup-production-logical.ts` uses `pg_dump -Fc --no-owner --no-privileges`, holds every local artifact only in `/dev/shm`, encrypts with AES-256-GCM using a scrypt-derived key, calculates SHA-256, uploads only the encrypted archive and a sanitized JSON manifest to `capture-tracker-production-backups`, downloads each object once to verify its checksum, and removes all temporary files in all cases. Its operator credential uses only Object Read & Write on that one bucket; it cannot use the document bucket, staging bucket, or account-wide bucket listing. The passphrase is process-only input and must be handled by the approved secret owner.

The command reports sanitized stage transitions for preflight, dump creation and validation, encryption and decryptability, checksum, manifest, private upload, remote read-back verification, receipt creation, and cleanup. A failure reports only the stage, controlled component name, exit/status classification, and cleanup result; raw provider bodies, command stderr, credentials, connection strings, backup contents, and customer data are never logged. A receipt is written only after both remote objects pass read-back checksum verification.

Every backup caller must explicitly set `CAPTURE_TRACKER_PRODUCTION_BACKUP_MODE`; there is no migration-check bypass or default mode. `PRE_MIGRATION_RELEASE` is permitted only with the `pre-acceptance` prefix and only when production is a completed, checksum-matching, ordered prefix of the clean exact release checkout: every applied migration must exist in source, none may be failed, rolled back, unknown, changed, duplicated, out of order, or ahead of source, and the remaining source migrations must be identified deterministically. `POST_RELEASE` is the strict ordinary/scheduled mode: production and source inventories must match exactly. Both modes require positive production-database identification, encryption, private destination verification, checksum verification, and plaintext cleanup before a backup can succeed.

Version-3 manifests record the explicit backup mode, authorized release SHA, production migration inventory at backup time, source migration inventory, exact pending migration names, encrypted object identity, encrypted artifact checksum, and backup format/version without secrets. A `PRE_MIGRATION_RELEASE` artifact represents production before the new release migrations: restoring it into the disposable recovery database must initially reproduce that earlier completed migration state. Advancing that restored copy through the identified pending migrations is a separate authorized recovery-verification step; never restore it over production.

The authorized backup bucket is private, not bound to the application Worker, has no public development URL, and uses lifecycle expiration only for `production/daily/` (30 days), `production/pre-acceptance/` (30 days), and `production/restore-verification/` (7 days). The document bucket is never a backup destination.

## Restore verification

`tsx scripts/verify-production-logical-backup.ts` accepts only the encrypted archive and its sanitized manifest, or a protected `/dev/shm` receipt that names that exact uploaded pair, plus a separately supplied disposable local database named `capture_tracker_restore_test`. The receipt is an operator-only handoff for a fresh backup drill; it is deleted after use and is never committed or logged. The verifier rejects every host except local WSL loopback on port 5432, and rejects production and staging names before it creates or drops anything. It verifies the encrypted checksum before decryption, decrypts only into `/dev/shm`, restores with `pg_restore`, and derives the source contract from the exact approved checkout. It then confirms the manifest-bound restored `_prisma_migrations` inventory, no rollback or failure state, the migration-state digest, tenant/accounting integrity, and sanitized restored data counts before dropping the disposable database and deleting the unencrypted archive. Post-release backups additionally verify the full source-derived schema inventory.

There is deliberately no maintained numeric migration literal. A future additive migration is included automatically when it is present in the approved source checkout and the fresh backup manifest. Post-release restores verify the exact source-derived structural inventory. Pre-migration restores verify the manifest-bound predecessor migration state, integrity, and sanitized counts before any separate recovery migration step. The sanitized manifest is the recovery contract and evidence.

For an actual recovery, stop application writes, obtain a separate explicit recovery authorization, restore into an isolated recovery database first, verify catalog and tenant/accounting integrity, and only then plan a separately authorized cutover. Do not reuse staging or restore over production for verification. Perform this restore verification periodically after each approved logical backup and preserve only sanitized evidence.
