# Production logical backup and recovery

Capture Tracker production remains on Neon Free. The available provider history is the current Free-plan window; it is not a seven-day PITR policy and no paid Neon snapshot schedule is used.

## Backup procedure

Run the backup only from native Linux/WSL. Provide the direct, unpooled TLS production connection only to that process through `CAPTURE_TRACKER_PRODUCTION_DIRECT_DATABASE_URL`; never put it in a Windows environment file, repository file, command argument, archive name, or log.

`tsx scripts/backup-production-logical.ts` uses `pg_dump -Fc --no-owner --no-privileges`, holds every local artifact only in `/dev/shm`, encrypts with AES-256-GCM using a scrypt-derived key, calculates SHA-256, uploads only the encrypted archive and a sanitized JSON manifest to `capture-tracker-production-backups`, downloads each object once to verify its checksum, and removes all temporary files in all cases. Its operator credential uses only Object Read & Write on that one bucket; it cannot use the document bucket, staging bucket, or account-wide bucket listing. The manifest records timestamp, database name, source commit, PostgreSQL version, encrypted archive size, checksum, sanitized data counts, and the ordered source-derived Prisma migration inventory with safe digests. The source database must have exactly that inventory in a completed, non-rolled-back, non-failed state before `pg_dump` starts. The passphrase is process-only input and must be handled by the approved secret owner.

The authorized backup bucket is private, not bound to the application Worker, has no public development URL, and uses lifecycle expiration only for `production/daily/` (30 days), `production/pre-acceptance/` (30 days), and `production/restore-verification/` (7 days). The document bucket is never a backup destination.

## Restore verification

`tsx scripts/verify-production-logical-backup.ts` accepts only the encrypted archive and its sanitized manifest, or a protected `/dev/shm` receipt that names that exact uploaded pair, plus a separately supplied disposable local database named `capture_tracker_restore_test`. The receipt is an operator-only handoff for a fresh backup drill; it is deleted after use and is never committed or logged. The verifier rejects every host except local WSL loopback on port 5432, and rejects production and staging names before it creates or drops anything. It verifies the encrypted checksum before decryption, decrypts only into `/dev/shm`, restores with `pg_restore`, and derives required migration, table, function, trigger, and named-constraint inventories from the exact approved source checkout. It then confirms that the restored `_prisma_migrations` records have every expected name, no missing or unexpected migration, no rollback or failure state, and the manifest-bound migration-state digest. It also verifies tenant/accounting integrity and that sanitized restored data counts equal the backup manifest before dropping the disposable database and deleting the unencrypted archive.

There is deliberately no maintained numeric migration literal. A future additive migration is included automatically when it is present in the approved source checkout and the fresh backup manifest. The migration inventory and source-derived structural inventory are the recovery contract; the sanitized manifest is the evidence that the backup and restored database matched it.

For an actual recovery, stop application writes, obtain a separate explicit recovery authorization, restore into an isolated recovery database first, verify catalog and tenant/accounting integrity, and only then plan a separately authorized cutover. Do not reuse staging or restore over production for verification. Perform this restore verification periodically after each approved logical backup and preserve only sanitized evidence.
