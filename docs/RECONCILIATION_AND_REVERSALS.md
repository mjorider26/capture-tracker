# Reconciliation and reversals

Reconciliation compares one business-owned checking, savings, or credit-card account with one statement period. In v1, the cleared book balance is `statement opening balance + cleared inflows - cleared outflows`; the difference is `statement ending balance - cleared book balance`. All values are Prisma Decimal values and a reconciliation finalizes only when that difference is exactly `0.00`.

Drafts contain only non-voided, account-matching transactions inside the statement dates and exclude transactions already used by another completed reconciliation. Draft selection is replaced atomically, version-gated, and audited. A completed record is immutable evidence; it cannot be reopened or deleted. The deterministic local demo begins with an empty checking-account draft ending at `$3,550.00`; selecting the four approved checking transactions reaches exact zero. `demo:restore` restores only that draft and its items, twice safely, without deleting audit evidence or changing Today values. Demo reversal remains preview-only.

Posted journals are corrected by a new `REVERSING_ENTRY`, never by line edits. The service derives all inverted lines, requires a concise reason, maps the selected date to an `OPEN` period, and preserves the original `POSTED` entry because the existing period trigger correctly prohibits changing historical locked-period status. A versioned conditional update is the concurrency gate and the existing `(businessId, reversalOfEntryId)` unique relation is the database duplicate-reversal backstop. The reversal header, lines, version gate, and audit event share one transaction.

Full PostgreSQL 17 validation covers the secure review baseline, deferred constraints, audit rollback, reconciliation and reversal services, and business scoping through `npm run check:accounting`. Deferred capabilities include bank feeds, statement uploads, automatic matching, reconciliation reopening, and a general journal editor.
