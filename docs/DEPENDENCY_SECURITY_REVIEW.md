# Dependency security review — Phase 9B.1

Audit dates: 2026-07-25. The baseline `npm.cmd audit --omit=dev --json` reported **12 high / 1 moderate** findings. After the supported remediation below, the same command reports **6 high / 1 moderate** findings (245 production packages). The full installation audit is intentionally broader because it includes build and test tooling.

Phase 9B.1 refresh recheck: Next `16.2.12`, OpenNext Cloudflare `1.20.2`, Prisma `7.9.0`, Wrangler `4.114.0`, and `pg` `8.22.0` remain current for their declared compatible ranges. No `@neondatabase/serverless` package is installed; application database access uses `pg` through `@prisma/adapter-pg`. Better Auth and its Prisma adapter were updated from `1.6.24` to compatible `1.6.25`, and `eslint-config-next` now matches Next `16.2.12`. The fresh production audit remains 6 high / 1 moderate; no unsupported remediation was applied.

Phase 9B.2 Linux workflow correction: the first non-deployment Linux verification run reached Next compilation but failed its TypeScript phase because the root application's broad include discovered `infra/aws/bin/capture-tracker.ts` before that package's dependencies were installed. The root TypeScript project now explicitly excludes the isolated CDK tree and its generated `.test-dist`/`cdk.out` directories. The dependency-separation gate verifies that exclusion, isolated CDK dependency ownership, dedicated infrastructure TypeScript coverage, generated-output ignores, and CI's application-before-infrastructure dependency ordering. This is a build-boundary correction only; a successful Linux OpenNext artifact remains required before changing any runtime advisory classification.

Phase 9B.2 second Linux run passed clean installation, Prisma deployment/validation, unit and database-integrity checks, standard Next `16.2.12` production build, TypeScript, routes, and static cloud checks, then failed during OpenNext bundling. `pg@8.22.0` conditionally requires locked transitive optional `pg-cloudflare@1.4.0`; its installed manifest publishes the Workerd `require` entry `./dist/index.js`, which exists after installation. Next tracing copied only that manifest into the generated server-function tree, so OpenNext could not resolve the Workerd entry. The supported correction explicitly lists only `pg-cloudflare` in `serverExternalPackages`; OpenNext `1.20.2` then uses its built-in Workerd-condition package-copy path and rewrites the copied manifest to select the Workerd exports. CI verifies the installed package before ordinary builds and the generated artifact after OpenNext bundling. `pg-cloudflare` remains a deterministic locked transitive dependency rather than a new direct declaration. A successful Linux artifact is still required before changing any runtime advisory classification.

Phase 9B.2 Linux artifact evidence (GitHub `verification`, 2026-07-26, commit `e34684a`): the Linux OpenNext build completed without a runtime-safety warning and saved `.open-next/worker.js`. `cloud:bundle:verify` measured **2,278 bytes**, passing the configured 3 MiB free-preview guard. `cloud:postgres:verify:artifact` passed: `pg-cloudflare@1.4.0`, its `dist/index.js` Workerd entry, and the transformed Workerd exports were present; the Worker had no unresolved `pg-cloudflare` external and the verifier found no excluded CDK, Prisma CLI/Dev, Vitest, TypeScript/ESLint, or local PGlite tooling in the generated server-function tree. The artifact and client/repository scans found no database URL, secret marker, credential, workstation path, or detected real-data pattern. The archived logs do **not** contain a PostCSS/Sharp runtime inventory or a direct `find-my-way`/Valibot artifact inventory. Therefore their absence and request-time reachability are not claimed. Decision **B**: fictional staging remains conditionally blocked pending that direct runtime inventory/reachability evidence, a fresh production audit, and the existing explicit later deployment authorization. Production, real-data approval, and customer onboarding remain blocked.

Phase 9B.3 adds `cloud:artifact:inventory` and `cloud:artifact:reachability` for the next non-deploy Linux run. The inventory reads the generated Worker/server-function executable inputs, copied package manifests, build manifests, and source maps separately; it classifies each target as bundled executable code, copied runtime package, manifest-only, build-time only, absent, or unresolved. Source-map and manifest strings are explicitly non-executable evidence. The sanitized `.artifacts/cloud-worker-inventory.json` contains only package/version/classification, artifact-relative paths, and reachability rules; CI uploads it with the sanitized audit summary and fails for an unresolved target or a request-time-reachable high target. Local synthetic fixtures cover PostCSS bundled/build-only, Sharp copied/absent, `find-my-way`/Valibot tooling or manifest references, Prisma/AWS exclusions, `pg-cloudflare`, source-map-only strings, unresolved imports, prohibited secret patterns, and absolute-path sanitization. The fresh audit endpoint remains unavailable locally, so the last known **6 high / 1 moderate** count is preserved rather than treated as current.

Phase 9B.3 Linux gate result (2026-07-26, commit `770668e`): the non-deploy Linux workflow completed the OpenNext artifact inventory and then rejected the report in `cloud:artifact:reachability` because at least one targeted high-severity package was classified request-time reachable. Copied package manifests below a generated server-function tree are Worker-runtime evidence; manifest/source-map strings alone remain non-executable. The workflow uploaded the sanitized report, but this local session cannot download the private GitHub Actions artifact without authentication and did not request credentials. Accordingly, the exact package/path must be read from that already-sanitized report before any remediation claim. This is nevertheless decision **C**: fictional staging is blocked by a reachable high target, not cleared on an assumption. The previous 2,278-byte entry measurement, `pg-cloudflare` packaging, tooling exclusions, secret/data scans, and compatibility flags remain valid only as their prior-run evidence; they do not override the new high-runtime block.

Phase 9B.4 reviewed the attached sanitized report for `4df990a`. The exact finding is `sharp@0.34.5`: `server-functions/default/node_modules/next/dist/server/image-optimizer.js` contains Next's conditional `getSharp()` `require("sharp")`, but the Linux artifact contains no Sharp package manifest, copied code, or metafile input. This is an unresolved conditional runtime external, not bundled or copied Sharp code. With the prior default image configuration, `/_next/image` could select that Next feature; Capture Tracker uses `next/image` only for fixed local public brand PNGs and accepts no image uploads, external image URLs, CSS, or runtime image-transform input. The vulnerable Sharp implementation therefore cannot execute from this artifact, but the broken conditional route must still be removed rather than waived. `postcss` is build-time only with no artifact evidence; `@img/*`, `find-my-way`, and `valibot` are build/tooling-only with no Worker entrypoint evidence. `find-my-way` remains under Prisma Dev and Valibot under Prisma CLI tooling.

The supported remediation is `images.unoptimized: true`: Next documents that it retains `next/image` while serving fixed sources unchanged, and OpenNext documents that runtime optimization needs a separate Cloudflare Images binding that is not approved for this no-cost fictional preview. The inventory recognizes this conditional reference as not request-reachable only when the generated artifact manifest itself records `config.images.unoptimized=true`; otherwise it remains unresolved. Adding Sharp `0.35.3` directly would not be an appropriate Worker fix because Sharp is Node-native and no runtime optimizer/binding is approved. This changes the pre-Linux decision to **B**, conditionally blocked pending a new passing Linux artifact report and fresh audit.

## Remediation performed

- Updated pinned Next from `16.2.11` to the compatible patch `16.2.12`. The audit still includes it, so this is a supported maintenance patch, not a claimed advisory fix.
- Moved the unchanged, exact `@opennextjs/cloudflare@1.20.2` from `dependencies` to `devDependencies`. It is imported only by build/development configuration and invoked by `cloud:build`; it is not application request code. This removes its six inherited findings from the production audit without an override, suppression, downgrade, or lockfile edit.
- Added `dependency:separation:verify`. It guards package placement; excludes OpenNext, AWS CDK, test, local-DB and Prisma CLI tooling from application runtime declarations/source; rejects unsafe dynamic package loading and process spawning in `src`; checks client/server boundaries, secret-free Worker config, no R2 staging binding, and no development server/tooling in the container runtime. It is static source/package evidence only and does **not** prove a Linux Worker artifact.

No `npm audit fix`, force fix, major downgrade, override, or advisory suppression was used. The offered `@opennextjs/cloudflare@0.2.1`, `prisma@7.8.0`, and `next@14.2.35` fixes are breaking/downgrade paths and were rejected.
